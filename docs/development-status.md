策略输出内部权重，再乘账户预算；空缺预算留现金。风控只减不增。20%回撤锁定时包括防御ETF在内的全部资产目标归零；退出是否成交由执行模型决定，滞留持仓必须记录。

财务因子接口接收已经核验的质量、价值分数输入，尚未把公开当前财务快照转换成可用于历史回测的因子。`original_version_verified`未知时证券被排除。信号要求已调整历史，不能自动使用未复权价替代。已建立适配边界，真实数据连续性、复权事件和交易资格仍待取得证据并验收。

## 运行方式

在`D:\vscode\Stock`运行；Python要求3.11及以上。系统核心和合成演示只使用标准库，不需要安装AlphaMaster或联网。

```powershell
python -B -m hybrid_quant status
python -B -m hybrid_quant check-data
python -B -m hybrid_quant demo
python -B -m hybrid_quant serve --port 8765
python -B scripts/run_tests.py
```

`status`显示本项目数据状态。`check-data`在历史证据不完整时返回退出码2。`demo`只接受`purpose=synthetic_engineering_demo`的配置，默认读取`config/demo.json`，输出至唯一的`reports/demo/<运行ID>`；它不读取本地真实行情，不输出投资有效性结论。测试临时文件保存在项目`.test-tmp`内，自动清理各测试临时子目录。

演示输出中的成交与账户曲线是工程测试值。模拟费用、交易规则、行业穿透和日期均为明确设定，不是对历史交易所规则或实际账户条件的验证。

`serve`启动后访问`http://127.0.0.1:8765`，按`Ctrl+C`停止。四个页面分别展示覆盖与准入、只读行情、策略配置、合成运行记录。页面的演示按钮使用项目`config/demo.json`生成新归档，界面不接受任意执行代码、写入真实行情或券商订单。配置修改仍通过本项目文件进行。

目录查询仅读取清单；日线查询先核验所选输出文件SHA-256，再验证整份文件的行数、日期和OHLC，返回最近200条，图示最近60条。`turnover`、`adjusted_close`、`available_at`和`tradable`未知时保留为空。原始成交量与股数估计保留不同口径。正式引擎快照契约见[接口说明](snapshot-bundle-contract.md)；当前注册数据不具备准入条件，该接口会拒绝载入。

属性测试（借鉴 AlphaMaster 的属性测试做法，2026-10-19）：新增 `tests/test_engine_properties.py`，用 Hypothesis 对设计文档的条款做属性检查——§3.1 的可观测边界、§10.3 的追加未来会话不改变既有视图、§5 的预算合并不超发与输入顺序无关。有效输入按构造成立而非用 skipTest 过滤，避免属性测试因大量跳过而失去意义。写的过程中它立刻抓到我自己命题的不严谨：追加一根在决策时刻本就可见的 bar 会合法地改变视图，原命题却把它当成违例；已改为只追加决策日之后的会话。hypothesis 作为 `test` 可选依赖声明，缺失时该模块整组跳过，CI 安装 `.[data,test]`。

多数据源冲突策略：[决策记录](source-conflict-policy.md)（**待确认**）。在引入第二个数据源之前必须先定这条规则，否则实现者会在代码里临时选默认值——静默取舍正是本项目要避免的。该文档把冲突分为数值、覆盖、时点、口径、完整性五类（口径差异并非冲突，是我在财务核验中已犯过一次的误判），并明确排除「优先级仲裁」与「行级合并」：前者让落选值退出证据体系，后者产出的行不再对应任何原始响应，哈希链随之断裂。

v0.2.2运行性能与加固：`DataSnapshot.known_history` 改为按快照记忆化并以二分定位交易日边界（cProfile显示其占回测耗时84%、单次回测6万次调用），合成快照只携带最近`history_window_sessions`（默认260，下限121）个交易日窗口——引擎最大回看121个交易日，演示的账户、订单、成交、决策输出与全量历史版本逐字节一致，快照内存从O(会话²)降为O(会话×窗口)。工作台`/api/overview`缓存15秒并在新建演示运行后失效，`DatasetRegistry.validate_for_backtest`缓存60秒（数据准入门会对全部8,554个已注册文件做全量SHA-256，约33秒/次，此前每次请求都执行）。实测100只证券×1,200会话回测18.3秒降到9.7秒、峰值内存633MB降到263MB；200只×2,400会话161秒降到45秒。HTTP服务读超时30秒、accept backlog 32、响应头不再暴露解释器版本；`.deps`本地依赖由`sys.path.insert(0,…)`改为`append`（核心包、脚本与测试辅助一致），已安装包优先，vendored副本只作回退，避免同名模块劫持；四个财报脚本由废弃的`fitz`导入迁移到`pymupdf`（保留旧版回退），`data`可选依赖设定版本下限并补声明`baostock==0.9.4`。

合成演示执行80个交易日，生成197笔订单并得到197笔模拟成交。初始v0.1.0[工程报告](../reports/demo/20261009T105850Z_48901e2a/report.md)和工作台生成的v0.2.0[工程报告](../reports/demo/20261009T112157Z_f0a9deb7/report.md)各自保留。归档8个输出文件哈希已核验，运行时Python代码哈希随归档保存；旧归档不因代码版本更新被覆盖。

2026-10-16 小范围可行性验证与全量验证工具：按“先小范围确认、再全量验证”的要求完成系统冒烟——status/check-data 行为符合设计（准入关闭）、208 项回归通过、合成演示 197 订单与基线一致、10 只证券×22 会话的真实序列自检通过、引擎门控保持时全现金而按记录范围放开后 58 笔订单全部成交且账务重建一致、工作台 `/` 与 `/api/overview` 正常（healthz 404 属未实现的 P2 项）。随后建成 §10.2 验收工具 `scripts/run_full_validation.py`：对任意序列输出风险匹配基准（同 universe 同预算的等权买入持有）、五组消融（各 sleeve 单开/无个股）、0/5/10/20 基点滑点敏感性（复用引擎 `FeeConfig.slippage_bps`）、60/20/20 时间划分（末 20% 封存样本外）、以及每项运行的账务红线（负现金、独立重建、无法执行减仓比例、实际超限）。`--relax-gates` 放开三门做机制检查并记录在案；不加则引擎按证据原状全现金。该工具有 4 项回归检查（合成序列，20 秒）。

集成检查独立重建成交现金与期末持仓，核对账户净值；相同配置与快照重复运行结果一致，追加未来交易日不会改变此前账户数值。首日收盘只产生信号，次日才出现持仓；未来财务观察被过滤。账户实际超限、不能按目标退出的持仓与陈旧估值均独立记录，不用目标合规冒充实际持仓合规。

## 后续开发顺序

1. 继续补齐真实时点数据与历史证券池：退市行情代码已补采完成，仍需全板块完整挂牌历史、停复牌与可成交状态、财务原始版本及完整公司行动；所有未知字段保留排除原因。快照序列构建器与财务因子层已就位，真实数据入序的前置是富化产品扩批、上交所当前证券参考与复权产品扩展三项（见数据准备进度 §8.8），因子可用性见 §8.9。
2. 数据子集一旦入序，立即运行三个单策略的独立回测与 §10.2 要求的基准/消融对比，输出无法成交比例与账务对账；在此之前不得提前宣称策略有效性。
3. 完善股数变化、差异化派息、税务、历史费用与涨跌停成交模型，再验证真实单策略与混合账户账务。
4. 增加虚拟策略贡献账本、行业暴露与成本归因、滚动验证和封存样本外报告。
5. 在现有工作台上增加研究对比、每日任务与模拟交易管理。

当前没有拆分/配股完整记账、真实历史规则适配、策略虚拟账本、实时行情或券商连接。已有本地数据保留原审计结果；不会因系统代码已能运行就自动放开真实回测。资金规模、权限和券商接口在相应阶段明确。
